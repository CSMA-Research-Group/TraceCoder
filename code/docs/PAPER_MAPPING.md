## 回滚规则的精确选择

论文概述写到没有提升时回到最优状态，但 **Algorithm 2 的第 6–8、13–15 行明确允许继续使用当前候选**。本实现按 Algorithm 2，而不是将概述改写为“没有提升就一律回滚”：

| 条件 | 决策 | 下一轮基线 | 最优状态 | 停滞计数 |
| --- | --- | --- | --- | --- |
| `S_attempted > S_best` | accept | 新候选 | 更新 | 归零 |
| `S_attempted == S_best` | continue | 新候选 | 不变 | +1 |
| `S_attempted < S_best` 且 `< S_previous` | rollback | 历史最优 | 不变 | +1 |
| `S_attempted < S_best` 且 `>= S_previous` | continue | 新候选 | 不变 | +1 |

`S_previous` 是上一轮**尝试的候选**的通过数，即便上一轮已回滚也保留这个值。下一轮插桩的失败反馈则与实际基线代码配对：回滚时重新使用最优版本的测试反馈，避免把退化候选的轨迹错配给最优代码。

返回结果始终保存最优实现，不将最后一个候选误作最优实现。持平继续探索、低于最优但不低于上一候选等分支都有独立行为测试。

## HLLM 的具体内容

每条失败记录包含：本次分析及修复计划、完整候选、实际错误反馈、通过数、代码差异、RM 决策。部分提升但仍未全通过的候选也属于失败记录。初始失败尚未经过修复，因此不计入修复历史。

后续 Analysis Agent 接收全部已有失败记录，提示其指出失败原因、总结应避免的错误并形成新计划。历史是同一任务内的数据，不跨题检索，不额外训练模型。第二轮的插桩建议来自第一轮分析输出。

## 与参考代码的区别

以 `news/` 的官方 main / WebDemo 提交为准。三个角色提示词正文从官方 `problem_processor.py` 提取并保持一致；服务不直接导入带全局状态和固定连接配置的旧运行模块。检查发现以下行为不能直接作为论文方法的完整替代：

- 参考历史列表只存部分计划及评测信息，没有完整保存所有候选代码；新实现保存 Algorithm 1 要求的全部主要字段。
- 参考主循环对非提升结果没有完整区分 Algorithm 2 的持平继续和相对上一候选退化；新实现逐分支实现该算法。
- 参考打印执行器仅用 `unittest` 收集测试，HumanEval 的 `check(candidate)` 可能不被执行；新执行器显式适配这两类入口及官方网页的顶层 assert，零测试不能成功。
- 原数据目录 `human_eval/data/test.jsonl` 含扩展断言，不能仅凭目录名当作原始 HumanEval。本实现用随附 `HumanEval.jsonl.gz` 作为 `humaneval`，`human_eval_plus` 的 Parquet 作为 `humanevalplus`，保留来源哈希。

## 明确记录的工程适配

1. **响应协议**：使用官方 `REPAIR_PLAN_START/END`、`Instrumentation_Suggestions_START/END` 与 `CODE: ... END_CODE` 格式，兼容已有 JSON 响应；请求、原始响应和解析错误均保存，不以预设代码兜底真实模型失败。
2. **插桩约束**：在论文提示约束上，增加 AST 结构保持与逐项测试状态一致检查。仅允许新增简单观测性 print，不允许在探针中调用函数或写变量。对象属性读取及运算仍可能有 Python 自定义副作用，因此不声称构成形式化语义证明。不满足检查时明确中断，不悄悄将带修复的插桩代码作为证据。
3. **测试计数**：HumanEval 在 `check(candidate)` 内逐断言捕获成功、失败与异常，避免首个失败掩盖后续测试。扩展集的 `assertion(candidate(...), expected, atol)` 按一次调用记录一个测试。unittest 按测试方法记录；顶层 assert 按实际执行的断言记录，保留前置赋值和循环，不通过正则改写比较表达式。原题面、输入和判定表达式不改动；该执行器不是原论文的评测器二进制复刻。
4. **证据上限**：原始每测试输出最多 12,000 字符，单次总输出保留预算 100,000 字符；截断明确标记。模型诊断视图最多选 8 个失败和 2 个通过测试，每项取末 50 行，记录省略项数。全部结构化测试结果另存。超过 250 KB 的模型请求明确报错，不静默丢弃失败历史。
5. **停止参数**：最多 5 轮遵循论文；默认 patience=2、执行超时=10 秒沿用参考配置，网页可调。论文实验采用 Python 3.10；本次本地验收使用 macOS Python 3.9.6，Docker 配置使用 Python 3.10，尚未在本机运行 Docker。
6. **失败范围**：初始语法错误、测试收集失败、超时和缺失依赖不能建立有效测试基线，会以错误状态保存并停止；当前网页不会把这些情况包装成已经进入正常轨迹修复。候选执行无效按 0 分参与决策，所有错误保留。
7. **教学模式**：演示案例的初始错误代码、诊断、失败和成功候选是公开可读的人工数据；仅用于展示与控制流程验证。真实模式不读取教学候选或基准参考解作为修复答案。

## 证据层级

- `fixture`：人工预设响应 + 新执行代码测试。
- `live`：真实模型请求响应 + 新执行代码测试，需之后配置接口。
- 历史记录打开：读取已保存 JSON，不发生新调用或执行。
- `verify_data.py`：随附参考解的执行器兼容性检查，不是模型实验。
- 论文表格与根目录旧 CSV：原材料，未作为本次复现实测结果导入页面。

本实现完成方法和演示闭环。若要进一步复现论文指标，还需要固定模型版本、完整依赖镜像、全量运行预算、基线实现和统计方案，并执行完整实验。
